## Start here — one measurement message

Keep your M0 files and `sdkconfig.defaults`; no erase or clean is needed to start M1. Continue editing `firmware/main/hello_world_main.c`. The board can stay unplugged for this exercise. Code review comes before you build and flash it yourself.

Eventually, perception will produce synthetic observations every 100 ms (10 Hz), while control checks the newest observation every 20 ms (50 Hz). A separate sensor task will represent other measurement work. Start by defining the message they will exchange.

A C `struct` groups related fields into one value. For example:

```c
typedef struct {
    uint32_t sample_number;
    float temperature_c;
} temperature_sample_t;
```

This defines a type; it does not take a measurement or create a task. `temperature_sample_t sample = {0};` creates one zero-initialized instance. `sample.temperature_c = 23.5f;` sets its temperature field; `f` marks a float literal.

**Your first exercise:** add `#include <stdint.h>` and define a type named `observation_t` above `app_main`, with these fields:

| Field | C type | Meaning and unit |
|---|---|---|
| `sequence` | `uint32_t` | Observation number, starting at 0; no physical unit |
| `acquired_us` | `int64_t` | Acquisition time since boot, in microseconds |
| `target_x` | `float` | Synthetic horizontal target position, normalized from -1 (left) to +1 (right); 0 is the center |

Inside `app_main`, before the existing loop, create one zero-initialized `observation_t` named `observation`, then set its `target_x` to `0.25f`. This is a made-up observation, not a camera reading. Leave the greeting and loop in place for now.

**Check before continuing:** ask for a code review. You should be able to distinguish the type `observation_t`, the variable `observation`, and the field `observation.target_x`. We will add a real timestamp and task communication in the next exercises; no build or hardware test is needed for this first check.

## Concepts

A task is a function with its own stack that the scheduler can suspend and resume. A queue copies messages between tasks. A notification wakes a task with little overhead. Priority matters when multiple tasks are ready; it does not make blocking I/O disappear.

In C, `uint32_t` is a fixed-width unsigned integer. A pointer refers to memory rather than copying its content. If a queued pointer refers to a local variable whose lifetime ends, the receiver has invalid data. Prefer small value structs for measurements.

Read the [FreeRTOS reference](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/freertos_idf.html) sections on tasks, queues and notifications as needed.

## Assignment

1. Create a message struct with sequence, acquisition timestamp and a synthetic measurement. Explain the unit of every field.
2. Create perception, control and sensor task functions. Begin with synthetic data, not hardware. Check queue/task creation failures explicitly.
3. Have perception produce a value at 10 Hz and control consume the latest value at 50 Hz. A length-one queue prevents a backlog of old observations; choose and document overwrite behavior.
4. Wake control from a periodic timer through a notification. Keep the callback short and choose normal or ISR-safe notification APIs to match callback context. Measure actual elapsed time with a monotonic microsecond clock.
5. Intentionally pause perception for 500 ms. Control must continue at its own cadence, recognize stale input and count stale events.
6. Log timestamps outside the critical path. Compute intervals in Python: `dt[i] = (t[i] - t[i-1]) / 1e6`. Report min, median, p95 and maximum deviations from 0.020 s and missed periods.

## Finish when

- Three tasks exist and communication/ownership is documented.
- A 60-second trace shows bounded behavior under a paused producer; no unbounded queue growth or busy-looping.
- You have measured timing instead of assuming a 20 ms delay produces an exact 50 Hz loop.
