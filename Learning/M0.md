# M0 — First firmware and physical inventory

[Start here](../START_HERE.md) · [Next: M1](M1.md)

**Goal:** identify what you actually have and run an ESP-IDF program on the board.

## Learn just enough

A source file is compiled into machine code, linked into firmware, and flashed into the board's nonvolatile memory. RAM holds runtime data; flash holds the program. A serial monitor displays output. A successful build alone says nothing about wiring or sensor behavior.

Read the [official getting-started guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/get-started/index.html). Use its macOS installation path and ESP-IDF Installation Manager or supported IDE setup. Select an explicit supported release and record it. Use documentation for that release throughout the project. Do not mix legacy driver snippets with current APIs.

## Assignment

1. Complete the physical checks in [HARDWARE.md](../docs/HARDWARE.md). Photograph board labels and identify its USB connectors and camera model. Keep personal information out of photos.
2. Install or activate ESP-IDF using the official instructions. Confirm `idf.py --version`, `cmake --version`, and `ninja --version` in the activated terminal. An IDE-managed environment may require its own terminal.
3. Compare `ls /dev/cu.*` before and after connecting the board with a known data cable. Record the new port. Connect no external peripherals yet.
4. From the repository root, copy the installed framework's `hello_world` example into `firmware/`. This folder currently contains only a placeholder. In an activated ESP-IDF terminal:

```sh
cp -R "$IDF_PATH/examples/get-started/hello_world/." firmware/
cd firmware
idf.py set-target esp32s3
idf.py build
```

5. Flash and monitor, replacing the port below with the observed port:

```sh
idf.py -p /dev/cu.YOUR_OBSERVED_PORT flash monitor
```

Exit the IDF monitor with Ctrl+]. Close it before another application opens the same port. Follow the vendor's boot-button procedure if automatic upload fails.

6. Change the greeting to identify your project and print a counter once per second using a blocking RTOS delay. Rebuild and upload. Explain why a delay lets other tasks execute.
7. Record the exact ESP-IDF version, board/module markings, flash configuration, port and successful command. Commit source/CMake and deliberate `sdkconfig.defaults`; keep generated build files out of Git. Export minimal configuration using your installed version's `idf.py save-defconfig` when appropriate.

## Finish when

- A clean build succeeds and the physical board prints your changed message after reset.
- You can distinguish compile, flash, reset, and monitor.
- The inventory explicitly marks confirmed, missing and uncertain items. The pin table is not silently filled with guesses.

## Explain in your words

Where does the program live after unplugging power? Why can a USB cable charge a board but fail to upload? What evidence proves your modified program reached the hardware?

**Evidence:** short boot log and version notes. No sensor functionality is established yet.
