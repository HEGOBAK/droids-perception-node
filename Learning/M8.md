# M8 — Integration, evaluation and mastery

[Start here](../START_HERE.md) · [Previous: M7](M7.md)

**Goal:** integrate the system and write a report you can defend from evidence.

## Integration order

Start with the last individually verified commit. Combine IMU + servo, then range, then camera, then telemetry and viewer. After each addition repeat the timing and power checks. Preserve a reproducible known-good state. Do not change wiring, gains and scheduler priorities simultaneously.

## Experiment set

1. **Static sensors:** repeat known tilt and range tests; report bias, spread and invalid fraction.
2. **Tracking:** fixed and moving targets under controlled lighting; record image error, saturation and loss/reacquisition behavior.
3. **Stabilization:** matched disturbance trials with compensation on/off, at least three repeats each; keep gains, target and mounting constant.
4. **Concurrency:** run camera and telemetry together for five minutes; report control period distribution, missed deadlines, stack/heap behavior, dropped frames and resets.
5. **Fault handling:** target absent, range timeout, sensor read failure, disconnected host and board reboot. Introduce electrical disconnections with power off; use software fault injection for live timing tests.
6. **Mapping:** fixed target and fixed base origin with controlled rotations; compare reconstructed positions to a ruler-based reference within the declared assumptions.

For every run save firmware commit, host version, calibration, rates, lighting, distance, supply, duration, and raw/decoded data paths. Separate calibration trials from final evaluation trials.

## Metrics you can explain

`RMS image error = sqrt(mean(e²))`; state whether e is pixels or normalized units. Report p95/worst timing deviation as well as average. Range bias is mean(measured-reference); missing readings belong in failure counts, not zero-valued error samples. Relative improvement is `(baseline-new)/baseline*100%`; undefined for zero baseline and possibly negative.

## Report and reproducibility

Fill [REPORT.md](../REPORT.md) using [requirements](../docs/REQUIREMENTS.md). Add actual build/flash/host commands only after they work. Record component/host versions and configuration. Keep a short demo and plots tied to measured datasets. Explain where AI helped and how you verified its output.

Run host tests and an ESP-IDF build from a clean checkout/environment, then verify on hardware. A successful host test does not prove electrical safety or timing. A successful hardware demo does not prove the parser handles corrupted packets.

## Finish when

- Every requirement has evidence or an explicitly stated limitation/clarification.
- A fresh reader can reproduce setup, calibration and the demonstration using your commands and wiring record.
- Your worklog contains your explanation of one real debugging episode.
- You can answer the questions below without reading a generated paragraph.

## Mastery check

Explain one sample's complete journey: photons → frame → centroid queue → PID → MCPWM pulse → physical motion, and range/IMU → packet → CRC check → coordinate transform → plot.

Predict what happens if camera rate halves, UART stalls, gyro bias doubles, the servo saturates, the base translates, or a second object enters the ultrasonic beam. Choose a measurement that would test each prediction.

Finally, change one justified design choice yourself, predict its effect, measure it and explain the outcome. Mark a milestone complete because you understand and verified it, not because a file exists.
