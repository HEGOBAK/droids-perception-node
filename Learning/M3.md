# M3 — Distance and servo independently

[Start here](../START_HERE.md) · [Previous: M2](M2.md) · [Next: M4](M4.md)

**Goal:** obtain valid range measurements and command safe servo movement before closing a feedback loop.

## Before wiring

M2 left the IMU on I2C (SDA41, SCL42). M3 adds two more devices, so pins and power need a plan first.

- Fill the [pin plan](../docs/HARDWARE.md#pin-plan-fill-before-connecting): record the IMU pins you already use, then choose TRIG, ECHO and servo GPIOs. Reserve every vendor camera pin now; M4 needs them and moving wires later is error-prone.
- Keep the M2 pattern: one module per device (`range.c/.h`, `servo.c/.h`, see [architecture](../docs/ARCHITECTURE.md)), timestamps on every sample, a validity flag instead of a fake value, and logs saved to `results/M3/`.

## Distance exercise

Verify your actual HC-SR04P supply, trigger requirements, echo level and measurement interval. The order listing is not a complete datasheet. Use a safe signal interface from [HARDWARE.md](../docs/HARDWARE.md): powered at 3.3 V the ECHO output may already be 3.3 V-safe, but measure it before connecting it to a GPIO.

1. Generate the specified trigger pulse and measure echo high time. A simple first method is a GPIO edge interrupt that records `esp_timer_get_time()` at the rising and falling edges; hardware capture (MCPWM capture or [RMT](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/rmt.html)) gives more precise edge times. Keep the interrupt short: record times only, compute in a task.
2. Set a finite acquisition timeout and schedule measurements slowly enough for the module (common modules need about 60 ms between pings; check yours). Never busy-wait for ECHO. On missing echo return invalid, never zero meters — the same rule as the M2 INVALID flag.
3. Calculate `distance_m = sound_speed_m_s * echo_seconds / 2`. For an illustrative 20°C approximation, 343 m/s and 2 ms yield 0.343 m. Speed changes about 0.6 m/s per °C. The MPU6050 temperature is the chip's own temperature, not the air's, so don't use it as air temperature. Target geometry also affects accuracy.
4. Compare against a ruler at 0.20, 0.50 and 1.00 m where your module and target allow. Collect 30 readings per distance; record bias, spread, failures and target surface (the M2 mean/std method applies directly).

## Servo exercise

Confirm external power and common signal ground before connection. Start unloaded; do not force the shaft manually while powered or drive into a mechanical stop.

- Signal: GPIO 14 from the [pin plan](../docs/HARDWARE.md#pin-plan-fill-before-connecting). SG90 wires are usually brown = GND, red = +V, orange = signal; check yours.

1. Read [MCPWM](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/mcpwm.html). Create timer, operator, comparator and generator objects according to the installed API. Put them in `servo.c/.h` like `range.c/.h`. The hardware then repeats the pulse by itself; no task or `vTaskDelay` (10 ms ticks) is involved in timing it.
2. Use the servo's documented frame rate and pulse range. A common starting frame is 20 ms, but verify the actual servo. Do not assume every SG90 accepts 500–2500 µs or reaches a true 180°.
3. Start at the specified neutral pulse; try only small offsets. At a 1 MHz timer resolution, each tick is 1 µs. An example 1500 µs pulse in a 20000 µs frame is 7.5% duty.
4. Calibrate a conservative usable angle/pulse interval with an angle reference. Limit both command range and rate. Save direction, neutral, limits, supply and load. M5's controller uses exactly these numbers (neutral, sign, limits), so keep them in one place in code.
5. Test range while the servo moves: keep the step 1 ping loop running. Look for resets, range outliers and power sag before blaming software.

## Finish when

- Range measurements include timeout/validity and measured errors at known distances.
- Servo commands are bounded and cause small predictable movements without resets or end-stop contact.
- You can account for each supply and every used pin; the pin plan in HARDWARE.md is filled.
